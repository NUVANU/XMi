# Discuss and refine one product module

Read this when interviewing after initial activation, including continued projects and document intake. The Owner should see the design taking shape each round. A module is a concrete product capability such as equipment rules, item design, an order flow or a report export; the generic interview stages are completeness prompts, not the module boundaries.

## Keep a visible design in the conversation

Each useful module round is one complete review brief, including after saving an answer. Use these sections in normal chat:

1. **模块当前设计**: show the whole relevant module table with known behavior, current status and representative results. Reconcile existing canonical/source material, including relevant untagged older claims. A three-row paraphrase of the latest reply is insufficient when other module rules already exist.
2. **待确定项与我的建议**: one numbered table with decision, alternatives/conditional dependency, host recommendation and its reason/impact. Present the important same-priority choices together, up to eight by default. Display other known dependent or later issues as context; do not withhold them until a separate round merely because they depend on the first choice. Use “如果 A，则建议 B；如果 C，则建议 D” rather than silently assuming A. Do not force eight questions or invent module scope.
3. **效果与冲突检查**: explain useful concrete results, conflicts with existing rules and consequences of the recommendations. Recommended conditions, example values and inferred effects are not adopted product facts.
4. **一次回复即可**: invite replies such as “1 按建议，2 选 B，3 改成……，4 暂定”. A clear “其余按建议” may ground new PROPOSED drafts only for the exact visible recommendations in that numbered brief; refresh and show the resulting scope. Ambiguous blanket assent needs clarification; formal confirmation remains the existing exact host review.

Only the Owner's actual explicit pacing request narrows the decision count. Do not carry forward 1 from earlier tool calls or short answers as an Owner preference. One active decision is acceptable when it is the only useful unresolved choice; explain why, while still displaying module context and known deferred issues. Concision means readable decisions and explanations, not automatically reducing every round to one question. A question-count maximum limits active decisions, not the design/current-status table or contextual dependencies.

Choose the Owner-requested module, or the most important unresolved concrete capability grounded in known scope. Stay with it over multiple rounds until its behavior is understood and the Owner wants to move on. Do not switch because a single answer covers a generic stage. If there is insufficient concept information to name a useful module, ask a short anchoring question first.

1. Present the current module design as a readable Markdown table. Use columns that suit the design, not one fixed schema for every product. Show meaningful rows, fields, values, rules and results from known content. Use “待定” for missing values. Mark Owner-stated but unconfirmed content “用户描述，待确认”, saved confirmed facts “已确认”, and AI alternatives or illustrative data “建议／示例，未采用”. Do not fill unknown cells with invented defaults. Do not demand that the Owner supply a finished table.
2. Explain the observable behavior in ordinary language. Walk through a concrete success example and a relevant boundary/failure example when they help expose a rule. Identify the inputs, triggering conditions, result and interactions with related modules. For numerical effects, state the assumed inputs/formula and show the calculation; an illustrative result is not tested balance or measured performance.
3. Discuss the important unresolved decisions in the brief together: default up to eight, or the Owner's explicit smaller maximum. Give a recommendation and reason for every material choice, with meaningful alternatives and trade-offs. If a recommendation needs unknown information, state that dependency and conditional options. Related dependent issues can be evaluated in the same message without adopting unchosen premises. Skip answered choices and avoid unrelated filler.
4. Accept ordinary replies, edits to a row/cell, multiple changes and unknowns. Map “第三行这样改” to the exact displayed row and source items. If the target or meaning is ambiguous, clarify that edit before saving it; do not ask again for unrelated answers. Rebuild the design, explain changes/effects, and present the next complete module brief. A changed-rows view is acceptable for a large table only alongside an accessible module overview and the pending-choice/recommendation table; do not return only the latest-answer recap and one edge question.
5. Compare changes against this module and related canonical content, including confirmed facts, proposals, exclusions and terminology. Distinguish an actual contradiction from an unresolved interpretation. Surface missing conditions and consequences; ask the Owner to resolve material conflicts. The deterministic checks are heuristic support, not comprehensive proof. Preserve the distinction between user, player and protagonist until a relationship is selected; ask earlier if the ambiguity changes the table's rules.

Keep the table and explanation in normal chat. Do not put a long table or raw JSON in a question/approval dialog. A question-count limit limits questions, not table rows or explanation. The design table describes product behavior; it is not a database schema, code structure or an XDev implementation task list.

## Canonical continuity and edits

Pass a stable, ordinary module name in `interview_module` on xmi_project_resume and xmi_answer_analyze. It is at most 80 characters. Answer patches receive `module:<name>` tags; retain those tags when saving the reviewed candidates. All canonical content remains in the existing Product Model. Do not save a duplicate table file, hidden conversation state or a second database.

`resume_packet.module_review` reconstructs saved rows for the explicit module, or the most recently touched tagged module. It includes proposals/confirmed rows, sources, links, versions and truncation flags. `review_brief` gives the mandatory response shape and decision maximum. `pending_decisions` contains existing open/blocking items, unresolved structured decisions and related open questions; supplement it with visibly unsaved semantic gaps found in the actual design. An ordinary Owner-stated PROPOSED rule is known content awaiting formal review, not automatically an unanswered question. Pending previews are bounded and may be partial. Its `completion` is always NOT_EVALUATED; all-confirmed or empty rows never imply completeness. `next_questions: []` means compose the complete contextual review brief, not stop or return one habitual follow-up.

Read full canonical items with xmi_project_get pagination and expected_version whenever a module row, sources, links or the snapshot is truncated. The module preview is not an exact approval payload. Old projects may have no module tags: obtain full known claims, reconstruct a table from those claims, cite their existing sources, and attach new grounded answers to the chosen module. Do not repeat intake, retag/confirm old facts silently, or claim an untagged old table was recovered automatically. Cross-module relationships require reading the relevant other module and global blockers.

The answer tool's module view is the saved state before the answer, not a saved revision. Save grounded Owner answers as PROPOSED drafts, refresh canonical state after each mutation, and rebuild the displayed design from the refreshed items. AI-created rows, inferred rules and suggested numbers stay visible as unsaved suggestions unless saved through their appropriate proposal/consent path. Never label AI suggestions as conversation-grounded answers merely because they were displayed in the chat.

Edits create new candidates with provenance and links to the affected items; do not overwrite a confirmed statement. Show the previous and proposed behavior when both remain active. A link or `supersedes` value alone does not reject or supersede the old item. Use the existing exact Owner rejection/confirmation paths when resolving the replacement. Do not hide the old rule from the table until the canonical action succeeds. Do not silently merge a conflicting new answer into an already confirmed table.

## Finish discussion and move on

Before proposing the next module, present the current module table, core rules, representative results, connections to other modules, remaining unknowns and a few observable acceptance examples. Check that relevant fields/ranges, conditions, transitions, failure behavior and cross-module effects are sufficiently clear for the selected scope. These are review criteria, not an automatic completeness score. The Owner may defer a nonblocking issue explicitly; retain its unresolved state and impact. If they choose to switch early, preserve the unfinished module and resume it later without forcing an interview restart.

At the module boundary, call the advertised xmi_module_review_prepare for the next batch of at most 50 ordinary pending rules tagged with this module, in canonical item order. The list states its size and how many items remain outside this batch. Confirmation covers only the displayed batch; after verified receipt and canonical refresh, prepare/display the next remaining batch until none remain. Zero pending items does not itself establish module completeness or readiness. Display its full numbered review_text in normal chat after the current design, examples, cross-module impact and unresolved choices. Keep unadopted recommendations separate from this exact adoption list. The Owner replies “确认好了” for this one current list, or gives numbered changes; changes invalidate the old list and require a fresh list after grounded drafts are saved. The native UserPromptSubmit bridge records actual Owner confirmation atomically; verify xmi_module_review_status plus canonical read-back before moving on. Do not open per-row confirmation forms. If the local bridge is unavailable, keep drafts and explain native hook trust/reload, without forcing repeated dialogs. Cloud connections use their advertised authenticated batch page until a genuine chat reply bridge exists there. Structured material choices and one-off item actions use the complete single-item native chat list and genuine reply grant described in tool-workflow.md; mode/risk/file/export gates remain independent. A request to continue/switch modules does not confirm rows or clear readiness blockers. Final readiness/compile/export remains xmi-audit-export.

## Examples of design views

For a skill module where known rules say automatic skills use a one-cell range, manual skills have no distance limit, learned cards leave the hand, same-name hand cards share cooldown, remote basic attacks remain remote, and taunt overrides target choice: show those rules together. The pending table can compare **taunt outside skill range** (recommend respecting range), **lowest health measure** (absolute versus percentage), **eligible target pool** (recommend selecting only valid in-range enemies) and **ties/invalid targets** (recommend a deterministic fallback). Explain how the range recommendation conditions the candidate-pool choice; ask for one numbered batch answer. Those recommendations are examples of unadopted options, not facts to copy into a game. The negative regression form is a recap of only “remote attack / lowest health / taunt” followed by “Does taunt at three cells extend range?” as the sole question with no other review.

- Equipment/skills: columns for skill, equipment combinations, triggering conditions, resulting damage/effect, constraints and status. Explain how changing an equipment attribute changes the outcome. If “build” is only a designer's label, preserve that as terminology; do not invent a player-facing profession/build-selection system. Compare only combinations supported by known rules; unknown damage numbers remain pending or explicitly illustrative.
- SaaS order flow: columns for current order state, event, allowed role, next state, visible result and exception. Walk through submission and cancellation/refund only if those capabilities are actually in scope. Discuss effects on inventory/payment/notifications without inventing integrations.
- Tool export: columns for input, selected scope, output format, naming/overwrite rule, error result and status. Demonstrate a valid export and an invalid input with labelled sample data. Do not imply that an illustrative export has run.

These are examples, not mandatory modules or product decisions. Use the Owner's vocabulary and actual product scope.
