# Technical solution interview

Use the same workflow for systems, SaaS, tools, mobile/desktop apps and games. Wait for confirmed users, core flow, data sensitivity, platform, deployment, scale, integrations and cost/maintenance preferences. Ask about existing technology/team skills and material constraints without requiring the Owner to know framework names.

Explain two or three compatible whole solutions in the Owner's language: client/frontend, backend if needed, persistence if needed, deployment, and game engine when applicable. Compare fit, maintenance, cost, privacy, offline behavior, lock-in and migration; the server catalog is a conservative starter, not exhaustive or verified support. Do not add accounts, cloud storage or backend merely because a technology supports them.

Read solution_review from project resume. Present why_it_fits, alternatives, trade-offs, risks and unresolved_inputs. For current versions, licenses, pricing, platform/export support and provider behavior, consult official primary sources and record dated findings as proposed solution_constraint items with real source_refs. If browsing is unavailable, keep those inputs unresolved; never claim live verification. Save/confirm material constraints with the existing exact review workflow. A version or price from memory is not evidence.

The Owner may choose a candidate, specify technologies outside the starter catalog, defer or explicitly delegate within constraints. Record a selected technology as solution_constraint with technology-choice/stack/engine tags. After Owner confirmation, resume to regenerate the blueprint; do not invent a selected_option_id on blueprint tools. The current blueprint tool approves its exact recommendation or delegates within it. To choose a different option, confirm that technology constraint first and review a fresh blueprint. A PROPOSED preference must not steer canonical selection. Resolve incompatible or excluded technologies before approval.

For games, clarify 2D/3D, visual/performance targets, platform, saves and state authority, plus networking only if applicable. Engine candidates do not prove export or performance compatibility; require a prototype where needed.

On the local native bridge, save the returned blueprint through xmi_item_review_prepare with an xmi_patch_apply request. Display the entire readable chat list; the next real “确认好了” reply grants only saving a PROPOSED blueprint. Consume that grant through xmi_item_review_commit and read back. To adopt or delegate afterward, prepare a distinct xmi_item_confirm request with the current binding and solution_disposition APPROVE_BLUEPRINT or DELEGATE_WITHIN_BLUEPRINT, display its full list and consume its own genuine reply grant. Explain the action and boundaries clearly; do not send the raw blueprint JSON or reopen a single-item popup. Hosts without the native bridge retain their authenticated review. Export uses the approved composition, alternatives and unresolved checks in XSpec. XDev owns code modules, scene/class layout, implementation tasks and verification; changes to approved material constraints require an amendment.
