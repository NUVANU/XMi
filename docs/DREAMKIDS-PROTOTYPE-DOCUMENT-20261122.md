# DreamKids prototype document flow

XMi exposes `xmi_prototype_preview` to a local host that sets `XMI_DREAMKIDS_PROTOTYPE=1`. The normal MCP catalog is unchanged. The preview takes the current project version and a structured interview summary with the first version’s behavior, observable checks, and the player or tool-user flow. It validates branching, offers a choice of visual format for a game when needed, and removes duplicate paths.

The DreamKids host creates one `DreamKidsDocumentSession` per authenticated account, chat and project. The host uses `show` to register the MCP result and renders the returned snapshot. It uses `answerChoices` for real user answers to the grouped questions and renders the replacement snapshot. Keep the displayed snapshot ID with the chat message. Route the authenticated user’s actual reply to `selectOption`; “确认输出开发文档” and its displayed option number generate the document. This path is a trusted host integration, so it is separate from agent-callable MCP tools.

The host supplies its trusted local export directory using the `DreamKidsDocumentSession` constructor option `{outputDirectory}`. The same chat choice approves an exact, immutable local export of the displayed design. XMi maps visible game facts to its profile, records projected confirmation events from the selection, runs the existing XUi and XDev conformance checks, and returns the result only after publishing and verifying the full sixteen-file package. The separate local confirmation store preserves the exact projected events and bytes across retries. A host requesting this publication receives a readiness error if any real gate fails. Hosts using the earlier in-memory constructor still receive candidates. The source project remains separate from the derived prototype project, and implementation authorization remains with the downstream host.

The preview supports new private prototypes. Its programmatic checks catch structural issues and recognized risk signals. Semantic contradictions can still survive keyword checks, so the displayed flow, selected answers and acceptance checks remain the review surface. Existing formal projects use their ordinary XSpec workflow.

Native review preparation checks whether the exact amendment can reuse the approved technical choices. The displayed list includes the carry-forward scope for eligible additions and bounded corrections of confirmed requirements, acceptance checks, or integration rules. Eligible revisions and the binding update commit together, and same-call validation uses the new version. The explicit `preserve_blueprint_choices: true` flag remains accepted. Review real solution changes through the existing path. The binding event is additive; a reader predating it needs an updated reader or the corresponding pre-upgrade backup.
