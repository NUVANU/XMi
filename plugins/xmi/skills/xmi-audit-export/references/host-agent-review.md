Use after local audit passes in the Owner-configured cycle, or on an explicit independent request. It is a second reading of the current design, not a prerequisite for XSpec export.

1. When the final confirmation receipt has `post_commit_review`, use its job and collection key directly. If no continuation was requested, call the advertised xmi_spec_review_start with the exact current version and genuine native session selector. Matching version, snapshot and scope reuse the same numbered review. Optionally supply interview_module for the current module's statements, directly linked settings and common context documents. A schema-valid compiled candidate is required. The reviewer receives a numbered index for the frozen readable specification, its changes including blueprint sections, linked acceptance, and separately indexed background. The Agent receives no full Product Model.
2. When host_job is returned, launch one host Agent with its exact task_name, message and fork_turns none. The assigned reviewer reads the required pages once and takes optional original passages only as needed. A missing page number is corrected once by the same reviewer. Previously verified pages stay in the same run. A bad read, an interrupted review or missing scope does not establish a result. Do not steer the reviewer, edit its answer or start replacement Agents after timeout.
3. Reuse the original start key/version/session/module to collect once. Never pass reviewer JSON as authority. Status is read-only and supports finding pagination.
4. In full-document results use delivery_action for each finding and delivery_triage for totals. Group only ASK_OWNER findings into one choice list, naming the linked criterion, impact and options. XMi checks VERIFY findings and missing context, reports unrun scenarios, reuses exact confirmed rules, and leaves FOLLOW_UP advice in the review record. A legacy blocking finding with no acceptance link still requires an XMi check.
5. Findings are advice. Even BLOCKING severity cannot confirm product changes, change readiness or grant formal assurance. Present actionable issues once through issue_handling. The genuine handling reply confirms exact selected changes; commit directly, validate, and continue the existing independent review after real changes. Reuse ignore/defer dispositions and ask only about unresolved rows. No acknowledgement of reports or review completion is required. Empty findings do not mean PASS.

Project/version and actual native Agent/material sources are checked. Host permissions remain inherited; this path does not prove permission isolation or exhaustive coverage. Old strict runs remain historical records under their original schema. Generic hosts without this adapter remain unavailable; continue the normal compile/validate/export workflow with truthful limits. Do not configure providers, billing, credentials or a new review platform.

Check responsibility/dependency, interfaces, state/data authority, failure/recovery and extension consistency. A full review that predates the current architecture cannot stand for reviewing it. Keep historical results. On a new confirmed version focus on changed items, linked criteria and direct impacts, with the current full documents as context. Do not request approval of the report or its process.
