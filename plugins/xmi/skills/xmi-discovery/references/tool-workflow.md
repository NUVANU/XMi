# Tool workflow for the current local XMi server

At finalization, inventory all known remaining confirmations before requesting approval. Use the advertised native xmi_item_review_prepare requests batch for compatible actions, display its complete numbered review once, then commit after one genuine reply. Do not repeatedly audit and ask about one setting at a time. Keep individual selected options/reasons explicit; if new facts invalidate a blueprint, refresh it after the fact batch rather than waiving its fingerprint. Export still requires exact file authorization.

Mode-risk corrections: inspect `exclusion_requires_split_ids` and read full affected items before choosing a disposition. `DEFER_OR_EXCLUDE` removes entire listed IDs in the frozen handoff contract. `RISK_SCOPE_SPLIT_REQUIRED` opens no approval form and writes nothing: present current versus future capability rows, propose separately sourced items, and obtain Owner review before retiring the old mixed item. Never hide retained features inside a free-text exclusion rationale. Legacy dispositions without the current projection provenance remain readable but need fresh risk review before solution approval/export; do not forge that provenance, edit the database, or claim old confirmation was replayed as new approval. New resolutions retain exact Owner rationale. Existing withdrawals preserve history. DOCX parsing failures/limits retain the original user-managed file; offer a smaller module or Markdown/TXT rather than repeated identical retries.

Discover actual configured XMi tools and read their input schemas before calling. Names below are semantic tool names; the host may namespace them. The current MCP envelope remains `schema_version: "0.1.0"`; Product Model/XSpec have their own versioned schemas. Never pass actor, owner_action, approved or an invented consent token.

## Read, propose, save, confirm

Local module/single-item review session routing: pass session_id from this turn's native XMi UserPromptSubmit context to xmi_module_review_prepare/status/commit and xmi_item_review_prepare/status/commit. The MCP process may have no CODEX_THREAD_ID; a real explicit route works without it. This identifier grants no Owner authority. Missing session raises CHAT_CONFIRMATION_SESSION_REQUIRED; a selector without a native hook record cannot prepare. Never guess another chat, ask the user to supply internal IDs or retry restart loops. Only actual native reply plus complete displayed-list verification adopts items.

1. Existing project: xmi_project_resume with the supplied project_id and interview_module when continuing a concrete module. Inspect snapshot_consistent and module_review truncation. Resume the saved design rows, including proposals; an empty module next_questions list asks the host to continue contextual table discussion, not stop. Use xmi_project_get with pagination and expected_version to obtain the current item/version/fingerprint you actually need. Do not create a replacement on PROJECT_NOT_FOUND without asking.
2. New project: xmi_project_create with initial_idea, actual source_ref and a stable idempotency_key; title/profile are optional. The host form must approve persistence. The resulting idea is still PROPOSED. Keep the returned project ID, never invent one.
3. Document start: after project creation/resume, briefly explain in the Owner's language which exact file will be read, that the purpose is to assess existing design/gaps/ambiguities/conflicts, and that the form approves reading, not adopting its claims. Then xmi_document_assess can read the exact Owner-selected Markdown/TXT/DOCX/PDF path only after its independent host form. The form shows the project and full selected path in ordinary language; never echo its raw technical payload as a second confirmation request. If the file is wrong, cancel and ask for the corrected file in chat. It returns proposed claims with file digest and source position. Save grounded selected claims as PROPOSED drafts through individual tool calls without per-item saving forms, then show the module/document summary for grouped Owner review; no document claim is automatically confirmed and the original file is not copied into XMi.
4. Answer: xmi_answer_analyze with project_id, current expected_version, answer, new non-colliding item_id, supported item_type, actual source_ref and the current interview_module. It returns a verbatim PROPOSED patch tagged with the module; candidate_patches and review_decisions keep that tag too. module_review contains saved pre-answer context, not the unsaved answer. Explain its limits; if structural_conflicts is nonempty, resolve the collision before attempting the patch.
5. Save: xmi_patch_apply with the reviewed returned patch, current expected_version and idempotency_key. A grounded non-blueprint PROPOSED draft sourced only from conversation turns or documents (including mixed references) saves as an agent draft without a host form. Preserve exact document source positions/digests. Blueprint proposals use the single-item native chat list below when available; saving still leaves them PROPOSED. Other non-auto-save proposals retain their applicable host review. Do not add fields to promote status or overwrite state. Tell the Owner what was saved and that it remains unconfirmed; refresh after each successful mutation before another command.
6. Ordinary module confirmation: after module discussion, xmi_module_review_prepare takes current project_id, expected_version and interview_module. Display its entire numbered review_text in chat; invite “确认好了” or numbered changes. Preparation saves only review bindings, never confirmed state. Each batch contains at most 50 pending ordinary items in canonical order; its complete text discloses the remaining count. A real reply adopts only that batch. After receipt and canonical read-back, prepare/display the next batch at the new version when pending rows remain; do not treat a partial receipt as whole-module confirmation. The trusted native UserPromptSubmit command independently verifies the actual next user reply and complete display, then persists GRANTED without a canonical write. Call xmi_module_review_commit with the exact project_id, expected_version, review_id and native session_id; it atomically consumes that private grant through domain events. GRANTED is not a committed result. A transient commit/sidecar failure keeps the grant retryable with the same binding and existing domain receipts; do not replace the list or ask for another approval. Any newer user reply (including a status question) or replacement list expires an uncommitted grant. On the next turn read xmi_module_review_status and refresh canonical state; never supply prompt/approved/actor or call per-row xmi_item_confirm to emulate the bridge. A different/ambiguous reply invalidates the list without confirmation. Changed state requires a new full list. If CHAT_CONFIRMATION_UNAVAILABLE, explain native plugin hook trust/reload and retain drafts. Structured relation/conflict decisions use the single-item list below, with exact selected_option_id and full current item/version/fingerprint. Cloud hosts without this native bridge keep the advertised authenticated batch review page.
7. Single-action native review: xmi_item_review_prepare takes schema_version, native session_id and a strict request containing operation xmi_item_confirm, xmi_item_reject, xmi_patch_apply, xmi_delivery_mode_select, xmi_mode_override_resolve or xmi_mode_override_retract plus that operation's current arguments. The patch variant supports a PROPOSED solution_blueprint only; ordinary grounded drafts still auto-save. Specify selected_option_id for a structured decision; solution_disposition APPROVE_BLUEPRINT or DELEGATE_WITHIN_BLUEPRINT for the distinct blueprint operations; intent REJECT and reason for rejection. A policy review displays mode/reason or the entire affected risk scope, old/new disposition, reason and effect; provenance stays internally bound. Display the complete review_text verbatim as the final reply, invite “确认好了” or changes, and wait. Preparation never writes confirmed state. Do not open old item/policy popups or shorten the content.
8. Native commit: the actual next UserPromptSubmit verifies full display and records GRANTED. xmi_item_review_commit accepts only project_id, expected_version, review_id and the same native session_id (plus schema_version); it consumes the private verified grant and applies the original staged action. No model-supplied approval is accepted. Read canonical state and xmi_item_review_status before reporting success. GRANTED means permission was received, not that saving succeeded; APPLIED has a verified commit receipt. The same commit retry is idempotent. A newer human reply or a replacement list expires an uncommitted grant. A changed project fails safely; refresh and review the changed content. Proposal saving remains PROPOSED; adoption, delegation and rejection remain distinct explicit events. Cloud without this native bridge uses its advertised authenticated review.

Do not compute fingerprints from a truncated statement. Use server-returned fingerprints; the applicable review must display the full exact content. If the review is too large, explain the limitation and ask for an explicitly narrowed candidate, not a shortened confirmation of unseen content.

Do not concatenate a whole module, transcript recap or several rounds of rules into one giant general-review candidate just to confirm it. Keep independent product rules as separate sourced drafts and present their complete module view together in chat. Ordinary confirmation forms display exact product content with technical provenance retained internally. On REVIEW_TOO_LARGE, no approval form or confirmation occurred: explain the issue, review the original full draft in chat, prepare separately traceable short rules without silently discarding or adopting the original, and refresh canonical state before review. Use a real batch-confirmation tool only if this connection advertises one; never invent a local equivalent. Do not immediately retry the unchanged oversized request or approve a truncated preview.

Each separately reviewed mutation gets its own stable idempotency key. Retry identical requests with the same key after uncertain delivery. If input changes, refresh and obtain fresh review with a new key. Do not use a fresh key to force a stale or declined action through.

## Delivery mode

- xmi_delivery_mode_get reads the single canonical selection and bounded history.
- xmi_delivery_mode_recommend takes an explicitly established intended_outcome: PROTOTYPE, CONTROLLED_MVP or PUBLIC_PAID_OR_LONG_TERM. Explain the returned recommendation; do not persist a mode from it.
- For a precise proposed mode and reason, call xmi_delivery_mode_get with proposal: {mode, reason}. Use its proposal_fingerprint and model_version with intent SELECT_MODE, change SELECT or UPGRADE and an idempotency_key. Native Codex sends these arguments with operation xmi_delivery_mode_select through xmi_item_review_prepare and the genuine chat commit above. Generic hosts call xmi_delivery_mode_select with bounded readable review; cloud retains its authenticated page. Do not substitute a chat-generated fingerprint.
- Refresh mode after success and reuse existing confirmed product content.
- `xmi_mode_risk_evaluate` reads the deterministic current risk floor. A blocking finding stays blocking until the Owner uses the exact current `xmi_mode_override_resolve` path or changes/rejects the underlying scope.
- `xmi_mode_override_retract` withdraws a confirmed override without deleting its history; the underlying risk becomes unresolved again. Native Codex uses operation xmi_mode_override_resolve/retract through the single-action prepare/commit path above, rather than calling the old form endpoints. CHAT_REVIEW_REQUIRED is a routing correction, not a request for more approval dialogs. Do not retry an unchanged old dialog or revive an earlier reply.
- `xmi_mode_gap_analyze` is read-only and shows what an upward mode target still needs. None of these tools may silently lower the canonical mode or a scoped minimum.

## Failure handling and scope

CONSENT_UNAVAILABLE means a form-gated action cannot happen in this host configuration. Do not emulate its approval through filesystem edits, another tool or forged arguments. The module-end and single-item chat exceptions require an actual natively delivered UserPromptSubmit receipt; no assistant-supplied quote grants authority. Conversation/document-sourced non-blueprint PROPOSED draft saving remains automatic and never counts as confirmation. Native hook trust and real desktop acceptance remain separate from isolated protocol tests.

For PROJECT_VERSION_CONFLICT, refresh and review changed content before a new request. For idempotency-key reuse, keep the original request intact or prepare a separately reviewed change; do not bypass the error. For likely-secret warnings, remove credentials before persistence without repeating them in the response. For corrupt snapshot/state, stop mutation and ask the local operator to inspect; this Skill has no generic recovery/migration tool.

Missing tools: offer clearly labelled unsaved discussion, not a shadow canonical store. Loading this Skill does not authorize installation, host configuration, arbitrary database access, export, implementation task generation or a readiness claim. When audit/readiness/export is requested and the tools exist, transition to `xmi-audit-export` rather than inventing a parallel workflow. F-2 real-XDev runtime evidence remains M10 work; F-3 effective Auditor isolation remains open.

For an explicit Owner pace, request question_count (1–8) on xmi_project_resume or next_question_count (1–8) on xmi_answer_analyze. Concrete module review_brief defaults to eight active choices maximum; stage suggestions outside concrete modules retain three. Omit the count or pass 8 unless the Owner actually requested a smaller maximum; a historical call with 1 is not such a request. Preserve separate source references and skip known answers. Show related dependent issues as conditional alternatives in the review brief rather than automatically serializing them into later turns.

For concrete modules, keep the same interview_module name and present the complete review_brief after saving/refreshing: current design, pending choices with host recommendations and reasons, effects/conflicts, one numbered batch reply. pending_decisions collects saved undecided items and related questions, not every known PROPOSED answer; its truncation flags require full read-back. Supplement missing semantic choices visibly without inventing canonical records. Resume defaults to the most recently touched saved tag; explicitly select another module on Owner switch. No tag, brief, empty question array or conversational acceptance grants formal confirmation, completion or export readiness.
